# iHelp Ch06 开发记录

## Brainstorm 定稿

用户本轮关键原话：

- 把客服系统里占位的分流器做成正式版，这是 Workflow 里最关键的节点。
- 指代消解结合对话历史，完整问题原样透传；Query 改写和指代消解一并处理。
- 退款退货、售后才做 Query 扩写，强制 JSON，只保留 `queries` 字段；扩写只在检索侧现查现用。
- 七类业务意图之外保留“其他”，意图只输出 `intent` 和 `confidence`，带边界 few-shot。
- 退款退货、售后先拿订单，再强制检索政策，最后只把“这一单能不能退”交给主力 Agent。
- 缺订单号不能猜，执行阶段用聊天流订单卡片选择；退款原因只在提交退款单时从固定类目选择。
- 前端使用 Vibe Coding 直接做，不走 TDD 和 code review 流程。

确认的决策：

- 整体走 architectural 流程。
- 保持 Ch05 的 LangGraph 父图和 checkpointer，不用新增编排组件。
- 订单选择器采用确定性的演示订单目录，`query_order` 与选择卡片共享同一数据源，避免随机结果造成决策不一致。
- 退款/售后核心子流程为 `订单选择 -> 确定性取单 -> Query 扩写 -> 多路政策检索去重 -> 置信闸 -> 主力 Agent`。
- 默认先用主模型保证准确率；保留低置信度升级路径，但默认关闭低成本优先模式。
- `其他` 是结构化兜底，不把怪问题硬塞给业务意图。

## Task 3：Query 扩写与多路检索

我这一步发的关键原话：

- Query 扩写强制 JSON，字段就 `queries` 一个数组；几条一起检索再去重合并；只对退款退货、售后做，简单 FAQ 不扩；扩写只在检索侧现查现用。

我的关键产出：

- 扩写服务：`app/services/retrieval_queries.py`

- 失败测试：`tests/ch06/test_retrieval_queries.py`

评审结论：

- 模型输出必须严格只有 `queries`，非字符串数组或多字段直接回退单查询。

- 多路检索按 `chunk_id` 合并并保留最高分；单条检索失败不阻断其它查询。

我拒绝或纠偏了什么：

- 没有把扩写后的查询写进知识库，也没有改变入库侧的一条知识一份存储。

翻车与返工：

- 多路结果最终仍复用现有 `assemble_evidence` 的防 Lost-in-the-middle 重排，因此测试不能按纯分数顺序断言；已改为断言最高分 chunks 首位且集合完整。

- 衣服买大了要换，意图识别到售后；选择订单后弹出换货理由选择框，类似退货理由。

确认的决策：

- 换货仍属于 `售后`，不新增意图。
- 核心子流程新增 `after_sales_action=exchange`。
- 订单选定后直接发 `exchange_form` SSE，不要求用户再次输入订单号。
- 换货原因固定为：尺码不合适、颜色或款式不喜欢、商品破损、少件或错件、质量问题、其他。
- 新增 `/api/exchanges/reasons` 和 `/api/exchanges`，复用 `create_ticket` 写入 `ticket_type="换货"`。

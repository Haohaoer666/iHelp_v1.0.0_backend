# iHelp Ch07 开发记录

## Brainstorm 定稿

我这一步发的关键原话：

- 全程走 Superpowers 流程，技能自动触发；产出不是可单测代码的任务，把 TDD 换成标注样例或评估集验证。
- 实现前涉及 FastAPI、SQLAlchemy、LangChain、LangGraph 的接口必须先走 Context7 MCP。
- 只管当前会话，不跨会话、不存用户画像。
- 每完成一个阶段就在 `dev-notes/ch07.md` 追记，不允许收尾时一次性补记。

我的关键产出：

- 设计分类：architectural。
- 方案选择：独立 `ContextManager` 包住模型调用，保留现有 LangGraph 图和 checkpoint。
- 设计 spec（已定稿，待提交）：`docs/superpowers/specs/2026-09-21-ch07-context-management-design.md`
- Context7 MCP v4.1.1 已实际连接，并核对 LangGraph 1.0.8、LangChain `trim_messages`、SQLAlchemy 2.0 async ORM、FastAPI lifespan/SSE 官方文档。

评审结论：

- 五个设计段依次确认：数据与边界、预算与三层边界、后台摘要与上下文拼装、持久化与接口、验证与交付。
- 用户以连续“确认”接受设计，没有授权更换指定技术栈。

我拒绝或纠偏了什么：

- 拒绝把所有裁剪和摘要都做成 LangGraph 节点；图执行完成前会等待节点，异步摘要仍要另起任务，反而扩大子图状态和中断恢复复杂度。
- 拒绝直接依赖 LangChain 内建 summarization middleware；它不能自然满足两个持久化锚点、逐段追加和不重写旧梗概。
- 不接受无用户标识的“全部会话”列表；定为轻量 `user_key` 认领会话，但仍严格按 `session_id` 隔离上下文。
- 不把工具结果写入 `messages` 表，也不把摘要伪装成 system message。

翻车与返工：

- 当前会话未预挂 Context7 MCP，`codex mcp list` 只有 `cua_repl` 和 `node_repl`。已按官方 `@upstash/context7-mcp` stdio 方式临时启动并完成查询，没有凭记忆写接口。
- `uv run` 读取用户级 uv cache 时遇到沙箱拒绝访问；后续验证优先直接使用项目 `.venv` 中的 Python，必要时再申请权限，不改变技术栈。

## Task 3：三层裁剪与固定顺序组装

我这一步发的关键原话：

- 最近的留原文，一个字都不压；中间层用户原话不动，客服只留开头，大块工具结果换成一行标识。
- 两个锚点只挪 id、不搬数据。
- 调用模型时顺序固定，梗概和证据合成一条挂在用户当前这句之后。

我的关键产出：

- 上下文数据合同：`app/context/models.py`
- 分层裁剪：`app/context/trimmer.py`
- 固定顺序组装：`app/context/assembler.py`
- 旧裁剪计数器接入校准口径：`app/core/memory.py`
- 失败测试：`tests/ch07/test_context_trimmer.py`、`tests/ch07/test_context_assembler.py`

评审结论：

- 层 1 保留完整消息，降级只改变 `layer1_from_msg_id`。
- 层 2 保持时间正序，用户原文不改，客服按配置截短，工具结果单行化。
- 层 2 超预算只产生摘要范围和触发标记，不等待摘要、不改 MySQL 原文。
- 模型输入第一条始终是固定 system；梗概、订单事实和证据统一放在用户消息之后的 human supplement。

我拒绝或纠偏了什么：

- 没有把摘要做成第二条 system message。
- 没有让裁剪器修改 `ChatState.messages` 或持久化原消息。
- 计划样例原先把层 2 误写成倒序，实际测试已纠正为时间正序。

翻车与返工：

## Task 4：事实摘要与后台任务

我这一步发的关键原话：

- 摘要提示词只提炼事实与诉求，对话里没出现的内容一个字不许编。
- 中间层攒到超预算就在后台起摘要任务，全程不阻塞用户当前这轮回复。
- 触发、开始、完成、跳过、失败全留痕，带覆盖边界和耗时。

我的关键产出：

- 摘要提示词与模型调用：`app/context/summary.py`
- 后台任务所有权：`app/context/tasks.py`
- 上下文和摘要日志：`app/context/logging.py`
- 失败测试：`tests/ch07/test_summary_service.py`、`tests/ch07/test_summary_tasks.py`、`tests/ch07/test_context_logging.py`

评审结论：

- 摘要 prompt 明确限定商品、订单号、手机号、诉求和未解决问题，要求删除寒暄。
- 摘要调用完成后只返回正文，Markdown fence 会被剥离，超过上限只截正文。
- `schedule()` 只创建任务并立即返回；慢模型验证了调用方不会等待。
- 同一会话已有摘要任务时记录 skip，不会并发重复压缩同一范围。
- `model_ctx`、`history_ctx` 和摘要生命周期均为单行结构化日志。

我拒绝或纠偏了什么：

- 没有让摘要合并旧梗概；旧梗概只作为后续模型背景。
- 没有在摘要失败时推进锚点。
- 没有让日志展示 API key 或工具内部敏感参数。

翻车与返工：

- prompt 首次写的是“禁止编造”，测试要求原文含“不得编造”以锁定无事实补写语义；已修正文案。
- 后台任务用进程内 `asyncio` 所有权实现，符合单 worker 约束；多 worker 不在本章范围。

验证结果：

- `tests/ch07`：`21 passed`

## Task 5：ContextManager 与 LangGraph 集成

我这一步发的关键原话：

- 指代消解和意图识别共用 history_ctx；Agent 打 model_ctx。
- 完整历史和精简版各走各的，互不影响。

我的关键产出：

- 上下文准备：`app/context/manager.py`
- 图入口节点：`app/graph/context_node.py`
- State 派生字段：`app/graph/state.py`
- 父图入口：`app/graph/builder.py`
- 理解节点共享历史：`app/graph/nodes.py`
- 意图历史输入：`app/graph/intent.py`
- Agent 固定顺序 model_ctx：`app/graph/agent.py`
- 持久化只写 assistant：`app/services/turn_logger.py`
- 集成测试：`tests/ch07/test_context_graph.py`、`tests/ch07/test_turn_logger.py`

评审结论：

- `prepare_context` 是现有父图之前的一个派生节点，不替换 `messages`。
- 历史预算失败时直接进入 fallback，在任何模型调用之前返回 `上下文预算不足`。
- 理解节点和意图分类器共享同一份 `history_ctx`。
- Agent 有 ContextPack 时只使用系统人设、层 2、层 1、用户消息和单条 human supplement；无 ContextPack 时保留旧兼容路径。
- `log_model_ctx` 每次 Agent 准备消息时输出实际消息栈；ContextManager 每轮输出 `history_ctx`。
- `TurnLogger` 不再写 tool 行，且存在 `current_user_message_id` 时不重复写 user。

我拒绝或纠偏了什么：

- 没有用 `RemoveMessage` 改写 checkpoint 中的完整历史。
- 没有把摘要、订单事实或证据挂成新的 system message。
- 没有让兼容测试强行依赖真实 MySQL；旧图测试通过 `context_manager=None` 保持无数据库边界。

翻车与返工：

- 直调 Agent 子图的既有测试没有 `session_id`，日志函数改为使用 `direct-agent` 兜底，避免把测试夹具问题带进生产状态。
- 新增历史共享测试后曾出现摘要前缀断言不一致；确认模型输入统一使用 `【历史摘要】` 后修正断言。
- SQLite checkpoint 文件测试仍受用户级 pytest 临时目录权限影响，已单独用序列化器验证 `ContextPack` 可 msgpack 持久化并恢复。

验证结果：

- Ch07 与既有图相关测试：`67 passed, 1 deselected, 1 warning`
- 唯一 deselected 项是已知 `tmp_path` 权限场景；ContextPack 序列化单独通过

## Task 6：Chat user_key、只读接口与启动资源

- 侧栏加载失败静默降级，不影响聊天。

- 接口测试：`tests/ch07/test_conversations_api.py`
- Chat 接口回归：`tests/test_chat_api.py`

评审结论：

- 新 turn 在进入图前写 user 行并返回 `current_user_message_id`，resume 不重复写 user。
- 同 session 的不同 user_key 返回 409；消息接口对其他用户返回 404。
- 消息接口只返回 user/assistant，tool 行不会进入侧栏回载。
- 启动时构造 ContextBudget、SummaryTaskManager 和 ContextManager；预算不足只打 critical 报警并让请求走 `上下文预算不足` fallback。

- 没有把 user_key 做成登录或画像系统。
- 没有提供会话删除、跨用户查询或隐藏的写接口。
- 没有等摘要任务完成才结束应用；shutdown 只做有限等待和取消，未完成锚点不推进。

翻车与返工：

- Chat 测试原先不控制 user 持久化，新增接口后会在流式响应内才触发数据库错误；改为在返回 `StreamingResponse` 前完成归属校验和 user 落库，因此 409 能正常返回。
- 新增 conversations 模块后先跑 RED 得到模块不存在，再补最小路由与 schema。

验证结果：

## Task 7：多会话前端侧栏

我这一步发的关键原话：

- 聊天页加会话侧栏，列出该用户全部会话，新在前、首问预览、已摘要标记。
- 「新对话」只是开新会话，旧会话仍在侧栏可切回。
- 侧栏加载失败静默降级，不影响聊天。

我的关键产出：

- 页面结构：`D:\std_selftest_frontend\index.html`
- 会话状态、侧栏渲染、切换回载和 user_key：`D:\std_selftest_frontend\src\main.js`
- 桌面/移动响应式样式：`D:\std_selftest_frontend\src\styles.css`
- 构建与浏览器验证：Vite build + in-app browser

评审结论：

- 侧栏按 `updated_at` 倒序，显示首问预览和已摘要标记。
- 切换旧会话会调用消息接口，清空当前聊天区并回载 user/assistant 原文。
- 「新会话」只生成新 session id，不删除旧记录；切换后可以继续发送。
- 侧栏请求失败只隐藏侧栏，不阻断输入。
- 桌面 1280 宽度没有横向溢出；390×844 移动视口使用横向会话带，没有遮挡 composer。

我拒绝或纠偏了什么：

- 没有把会话列表做成后端可变 CRUD；仍是两个只读接口。
- 没有让历史回载失败清空当前聊天。
